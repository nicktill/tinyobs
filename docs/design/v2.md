# TinyObs V2: architecture review and design

Status: proposed · Scope: whole repository at `d402670`

This document is the review of TinyObs V1 and the design for V2. Implementation
follows it in small PRs (see [Roadmap](#roadmap)). Where a decision was made on
measurements, the measurements are linked.

## 1. Product contract

> TinyObs is a single-binary, local-first metrics server for developers who want
> production-style application metrics without operating an observability stack.

```
tinyobs                     # one binary, one port, one data directory
open http://localhost:8421  # immediately see what your application is doing
```

It is not a smaller Prometheus. It borrows Prometheus's data model, query
language and HTTP API because those are the standards people already know, and
it implements a small, tested subset of them. The product is the first five
minutes: point it at an application, and see request rate, errors and latency
without writing a query or a config file.

### Who it is for

- A developer running one or a few services on a laptop who wants to see what
  their instrumentation says before it reaches production.
- CI and demo environments that need a metrics backend with no setup.
- People learning how a metrics system works. The codebase stays small enough to
  read.
- A small production deployment (a side project, an internal tool, a single VM)
  that wants real metrics without running a stack. This is supported but not
  the primary target: TinyObs is a single node with no replication, so it
  suits workloads where losing monitoring during an outage of that node is
  acceptable. Section 10 lists what a production deployment needs.

### Workload targets

Everything below is designed and tested against these numbers. They are also the
limits: TinyObs degrades predictably, with explicit errors, beyond them.

| Dimension | Target |
|---|---|
| Active series | up to 10,000 (hard cap 50,000, configurable) |
| Ingest | ~700 samples/s typical; 50,000 samples/s sustained ceiling |
| Retention | 72 hours by default |
| Disk | about 13.6 bytes/sample: ~2.4 GB at 10k series × 15s × 72h, ~240 MB at 1k series |
| Dashboard query latency | < 150 ms for 1 h windows over 1,000 series (measured ~125 ms); ~15 ms at 100 series |
| Startup | < 1 s at 10,000 series |
| Memory | < 200 MB RSS at 10,000 series |

Disk is bounded without a size-based limit: `max series × (retention / interval) × bytes/sample`.

## 2. Review of V1

Severity: **P0** returns wrong answers or loses data. **P1** is a serious
correctness or reliability problem. **P2** is an architectural or product
problem. **P3** is polish.

### P0

1. **Query evaluation aligns raw sample timestamps instead of evaluating at
   steps.** `sum(...)`, `a / b` and `metric * 2` combine points only where two
   series have identical timestamps, which in practice is almost never
   (`pkg/query/executor.go` `aggregate`, `applyBinaryOp`). A number literal
   produces step-aligned points while selectors return raw timestamps, so
   `metric * 2` is usually empty.
2. **Unsupported label matchers are silently dropped.** `{code!="200"}`
   returns every series (`executor.go:153`).
3. **The parser never fails.** An unexpected token parses as the constant `0`
   (`parser.go:170`); truncated input such as `rate(x[5m]` is accepted.
4. **Compaction stores statistics as label values.** `__sum__`, `__count__`,
   `__min__` and `__max__` become labels (`pkg/compaction/types.go:50`), so every
   5-minute bucket creates a new series, and those series are returned next to
   raw data by the same selectors.
5. **Histograms are deltas, counters are cumulative.** `Histogram.Flush` resets
   buckets after each export (`pkg/sdk/metrics/histogram.go`), so `rate()` of a
   bucket is meaningless. The 10 s bucket is also labelled `le="+Inf"`
   (`formatBound`) and there is no real `+Inf` bucket, so any quantile estimate
   is wrong.
6. **Data race in the query path.** One `Executor` is shared by all HTTP
   requests and mutates `samplesLoaded` per query (`pkg/query/handler.go:25`,
   `executor.go:62`).

### P1

7. `rate()`/`increase()` differ from Prometheus. They don't extrapolate to the
   window edges, they clamp resets to 0 instead of compensating, and they
   ignore the step (`executor.go:507`).
8. The `/api/v1/*` endpoints are not Prometheus-compatible.
   - Instant results use `values` instead of `value`.
   - Invalid parameters silently fall back to defaults.
   - Errors are not in Prometheus's error shape.
   - `labels`, `series`, `label/<name>/values`, `metadata` and
     `status/buildinfo` are missing, so Grafana's metric browser is empty.
9. The SDK drops its final batch on shutdown: `Stop()` cancels the context
   the last flush then sends with (fixed in #42).
10. Counters and gauges send one sample per `Inc()`/`Set()`. At 1,000 req/s
   that is 1,000 stored samples/s per series (`pkg/sdk/metrics/counter.go:36`).
11. The context-timeout wrappers in `pkg/storage/badger` return early, but the
    Badger transaction keeps running in its goroutine.
12. `Delete` collects every key into one transaction and will hit
    `ErrTxnTooBig` on large retention sweeps.
13. Compaction loads the full 12-hour raw window of all series into memory.
14. Storage costs 47 bytes/sample: JSON plus the full label map on every
    sample. Label filters are a post-scan; one series over 6 hours takes
    ~650 ms to read. `Stats()` is a full scan.
15. Instant queries return the last raw sample with its own timestamp, not the
    value at the evaluation time.
16. Cardinality tracking is in memory only and resets on restart.

### P2

17. **Ingestion is a proprietary SDK plus a JSON protocol.** Applications
    already instrumented with Prometheus client libraries or OpenTelemetry
    can't send data without code changes.
18. **Not a single binary.** The UI is served from the relative path `./web`,
    and Chart.js loads from a CDN.
19. **Too many query surfaces:**
    - `/v1/query`, `/v1/query/range`, `/v1/query/execute` and
      `/v1/query/instant`.
    - `/api/v1/*`.
    - A WebSocket broadcaster that pushes raw samples.
20. **Unsafe defaults:**
    - Binds all interfaces.
    - Write endpoints are unauthenticated.
    - No request body limits.
    - `config.QueryTimeout` is defined but never applied.
21. **The dashboard misleads:**
    - Infers metric type from the name.
    - Plots counters raw.
    - Labels sample counts as "series".
    - Puts Go runtime metrics first.
22. **Docs are inaccurate:**
    - Links to `docs/` and `TESTING.md` are dead.
    - The README SDK example never reaches its metric code.
    - "PromQL", "Grafana-compatible", "~5,000 lines" and "240x compression"
      are all overstated.
23. **The 5m/1h downsampling machinery** is not needed for a tool whose data
    lives for days.

### P3

24. Comment noise (`CRITICAL FIX:`, `PERFORMANCE FIX:`), unverified
    performance claims in comments, emoji logging, and screenshots showing a
    desktop and Dock.

## 3. Principles

1. **Never return a plausible-looking wrong answer.** An error beats an empty
   result, and an empty result beats a wrong one. Malformed and unsupported
   queries are errors.
2. **Standards over custom protocols.** Prometheus exposition, OTLP, the
   Prometheus data model and the Prometheus HTTP API.
3. **Measured over speculative.** No complexity without a benchmark showing it
   pays at the target workload.
4. **User labels and internal metadata are separate namespaces.** Storage never
   encodes its own state as labels.
5. **Small interfaces, few knobs.** A flag exists only when a user has a real
   reason to change it.

## 4. Data model

- **Series:** a set of labels sorted by name, including `__name__`. Identity is
  the full label set.
- **Names:** metric and label names match `[a-zA-Z_:][a-zA-Z0-9_:]*` (label
  names without `:`).
  - Names starting with `__` are reserved. Ingest rejects them, except
    `__name__`.
  - OTLP names are translated to this form (section 6).
- **Values:** label values are non-empty UTF-8. An empty value means the label
  is absent, as in Prometheus.
- **Limits:** at most 32 labels per series. Names ≤ 128 bytes, values ≤ 1 KiB.
- **Samples:** `(timestamp int64 milliseconds, value float64)`. Timestamps are
  strictly increasing per series.
  - Re-sending an identical sample is ignored.
  - A different value at the same timestamp, or an older timestamp, is
    rejected and counted (`tinyobs_samples_rejected_total{reason}`).
- **Staleness:** a special NaN marks the end of a series. The scraper writes it
  when a series disappears from a target or the target fails. Queries treat it
  as absence, so dashboards don't draw five minutes of stale data.
- **Types:** counters and histograms are cumulative.
  - A histogram is `_bucket{le}` (including `le="+Inf"`), `_sum` and `_count`.
  - A summary is quantile gauges plus `_sum` and `_count`.
  - Delta temporality is converted nowhere; it is rejected with an explicit
    message.
- **Metadata:** type, help and unit are stored per metric family in their own
  keyspace, never as labels.

## 5. Storage

Decision: [ADR 0001](../adr/0001-storage-layout.md). In short, one Badger key
per sample, binary-encoded, with ZSTD block compression and an in-memory label
index.

```
s <series id:8>                 → encoded label set
d <series id:8> <timestamp:8>   → float64 (8 bytes)
m <metric name>                 → metadata (type, help, unit)
```

- **Series IDs** come from the label hash, with a linear probe on collision
  (salvaged from PR #37). They are stable across restarts.
- **The index** (ID ↔ labels, postings by label name and value, and each
  series's first and last timestamp) lives in memory. It is rebuilt at startup
  from `s` keys plus one key-only seek per series.
- **Selectors** resolve through the postings. Samples are read with one prefix
  seek per series.
- **Durability:** a write is acknowledged after Badger's write batch is
  flushed. Badger's value log is the write-ahead log. A crash loses nothing
  that was acknowledged; section 10 tests this with `kill -9`.
- **Retention** runs hourly. For each series it deletes keys older than the
  cutoff in bounded write batches, then removes series with no data left.
  Badger compaction reclaims the space.

### Alternatives considered

The six designs were measured on the same workload (2,000 series, 15 s
interval, 6 h). The measurements are in commit
[`8b7ef22`](https://github.com/nicktill/tinyobs/commit/8b7ef22).

- **Gorilla chunks with a WAL** would save ~40% disk (8.0 vs 13.6 B/sample) and
  query ~3× faster. The costs: about 4× the storage code, half the ingest rate,
  ~40× slower startup, and a WAL whose recovery must be proven. At the target
  scale both designs fit comfortably, so the simpler one wins.
- **Chunks persisted only when full** (PR #39) lose up to 30 minutes of data per
  series on a crash. Rejected.
- **Time-partitioned keys with `DropPrefix` retention** would avoid delete
  tombstones, but `DropPrefix` blocks writes while it runs. Rejected for now;
  revisit if retention cost shows up in profiles.

## 6. Ingestion

Two standard protocols, and nothing custom:

| Path | For | Notes |
|---|---|---|
| **Prometheus scrape** | anything exposing `/metrics` | `tinyobs --scrape localhost:2112`, repeatable. Text exposition format (0.0.4) and OpenMetrics text. `up`, `scrape_duration_seconds` and `scrape_samples_scraped` are recorded per target. Staleness markers are written on disappearance or failure. `job` and `instance` labels are set as in Prometheus. |
| **OTLP/HTTP** | OpenTelemetry SDKs and Collector | `POST /v1/metrics`, protobuf or JSON, gzip allowed. Translated as Prometheus does: `job` = `service.namespace/service.name`, `instance` = `service.instance.id`. Name sanitization adds `_total` for monotonic sums, unit suffixes, and `_bucket`/`_sum`/`_count` for histograms. Cumulative temporality only; delta and exponential histograms are rejected per data point, with a count in the OTLP partial-success response. |

The **TinyObs Go SDK** stays as a thin convenience layer for the example app and
for people who want three lines of setup:
- It aggregates in memory.
- It exports cumulative OTLP/JSON every interval.
- It adds no protocol of its own.

People who already use `prometheus/client_golang` or OpenTelemetry need nothing
from it.

**Prometheus `remote_write`** is not in V2. It is cheap to add later if people
want to point an existing Prometheus or Alloy at TinyObs.

## 7. Query engine

A new package, `pkg/promql`, implements a subset of PromQL. Every supported
feature either matches Prometheus's results or is a bug. Anything outside the
subset is a parse or evaluation error naming the unsupported feature.

**Evaluation model (Prometheus semantics):**
- An expression is evaluated independently at each step `t` in
  `[start, end]`.
- An instant selector takes the newest sample in `(t − 5m, t]` and ignores
  stale markers.
- A range selector takes the samples in `(t − range, t]`.
- `offset` shifts both.
- Results are assembled into a matrix by label set.
- All selector data is fetched once per query for the widest window any step
  needs.

**Supported:**

| Area | Supported |
|---|---|
| Selectors | instant and range, `=` `!=` `=~` `!~` (anchored), `offset`, subqueries (`expr[1h:1m]`) |
| Operators | `+ - * / % ^`; `== != > < >= <=` with `bool`; `and or unless`; `on`/`ignoring`; `group_left`/`group_right` |
| Aggregations | `sum avg min max count group stddev stdvar topk bottomk quantile`, with `by`/`without` |
| Range functions | `rate irate increase delta idelta deriv predict_linear resets changes absent_over_time`, and `avg/min/max/sum/count/last/present/stddev/stdvar/quantile_over_time` |
| Other functions | `histogram_quantile` (classic buckets), math (`abs ceil floor round sqrt exp ln log2 log10 sgn`, trigonometric), `clamp clamp_min clamp_max`, `time timestamp vector scalar absent`, `label_replace label_join`, `sort sort_desc`, date functions |

**Unsupported (explicit error):** native histograms and their functions, the `@` modifier, duration expressions, `count_values`, `limitk`/`limit_ratio`, `holt_winters`, `sort_by_label`, `mad_over_time`, and recording rules.

Subqueries, `deriv` and `predict_linear` were first listed as unsupported. They
were added during implementation because real dashboards use them (for
example "when will this disk fill?") and the conformance suite covers them.

**Limits:**
- 30 s timeout per query.
- 11,000 points per series (Prometheus's limit).
- 5 million samples loaded per query.

Each limit produces an error that names the limit.

**Conformance.** A test harness runs Prometheus's own PromQL test files
(`promql/promqltest/testdata/*.test`) against the engine.
- Every test must either produce Prometheus's expected result or fail with an
  "unsupported" error. A wrong answer fails the build.
- Cases that need native histograms are skipped.
- The files are Apache-2.0. They are not copied into this repository: the
  harness downloads them at a pinned Prometheus commit into an ignored cache
  (`make promql-compat`, also run in CI).
- Targeted cases written for TinyObs live in the repository.

## 8. HTTP API

One API surface, Prometheus-compatible, plus the OTLP receiver.

| Endpoint | Purpose |
|---|---|
| `GET/POST /api/v1/query`, `/api/v1/query_range` | PromQL |
| `GET/POST /api/v1/series`, `/api/v1/labels`, `/api/v1/label/<name>/values` | discovery (Grafana, UI autocomplete) |
| `GET /api/v1/metadata` | type, help and unit per metric |
| `GET /api/v1/status/buildinfo`, `/api/v1/status/tsdb` | version; cardinality stats in Prometheus's format |
| `GET /api/v1/targets` | scrape target health |
| `POST /v1/metrics` | OTLP/HTTP ingest |
| `GET /metrics` | TinyObs's own metrics |
| `GET /-/healthy`, `/-/ready` | liveness and readiness |

Responses, errors (`{"status":"error","errorType":"bad_data","error":"…"}`),
status codes, time formats (RFC 3339 or Unix seconds) and duration formats
(`5m` or float seconds) follow the Prometheus documentation. Invalid parameters
are `400`s, never silent defaults.

**Removed:**
- `/v1/ingest`, `/v1/query`, `/v1/query/range`, `/v1/query/execute`,
  `/v1/query/instant`.
- `/v1/stats`, `/v1/storage`, `/v1/cardinality`.
- `/v1/export`, `/v1/import`.
- `/v1/ws`.

## 9. UI

Embedded in the binary with `go:embed`. It uses vanilla JS modules with no
build step, and one vendored chart library (uPlot, ~50 KB) instead of a CDN
dependency. It polls the query API; there is no WebSocket.

1. **Services (home):** one card per `job`.
   - Card metrics: request rate, error ratio and p95 latency, each with a
     sparkline, plus when the service was last seen.
   - The card links to the service page:
     - requests by route;
     - errors by status class;
     - p50/p95/p99 latency;
     - runtime metrics collapsed at the bottom.

   HTTP metrics are detected by explicit, documented rules. First the
   OpenTelemetry semantic conventions (`http_server_request_duration_seconds`
   with `http_response_status_code` and `http_route`), then the Prometheus
   conventions (`http_requests_total` with `code`/`status`, and
   `http_request_duration_seconds`). A service without them shows its metrics
   plus a short "how to get RED metrics" note, not an empty chart.
2. **Explore:** a PromQL editor with autocomplete from the discovery API.
   - Counters get a one-click `rate()`.
   - Axes are unit-aware, using metadata and the `_seconds`/`_bytes` suffixes.
   - Mixed units split into separate panels.
   - The URL holds the full state.
3. **Metrics:** a catalog showing type, help, series count and highest-
   cardinality labels, from `/api/v1/status/tsdb` and `/api/v1/metadata`.
4. **System:** TinyObs itself.
   - ingest rate and rejected samples by reason;
   - series versus cap;
   - disk;
   - scrape target health.

The time range is selected in the header and shared across pages.

## 10. Operations and security

```
tinyobs [--listen 127.0.0.1:8421] [--data ~/.tinyobs] [--retention 72h]
        [--max-series 50000] [--scrape host:port[/path]]... [--scrape-interval 15s]
        [--auth-token TOKEN] [--tls-cert FILE --tls-key FILE] [--open]
```

- **Defaults:**
  - Listens on loopback only; a warning is printed when bound to a
    non-loopback address.
  - Data lives in `~/.tinyobs`, printed at startup, regardless of the working
    directory.
- **Optional authentication.** Set `--auth-token` (or `TINYOBS_AUTH_TOKEN`)
  and every endpoint except `/-/healthy` and `/-/ready` requires it.
  - Clients send it as a bearer token, or as the password of HTTP Basic auth.
    Basic auth means browsers prompt for it natively, and Grafana, Prometheus
    and OTLP exporters already support both forms.
  - There are no user accounts or roles.
- **Input limits:**
  - 16 MiB request bodies, applied after gzip decompression.
  - Label count and length limits (section 4).
  - The series cap.
  - Query limits (section 7).
  - Scrape responses capped at 16 MiB, with a 10 s timeout.
- **Shutdown:** SIGINT/SIGTERM stops scraping, drains HTTP, and flushes and
  closes storage.
- **Backup:** `POST /api/v1/admin/tsdb/snapshot` writes a consistent backup
  of the database under `<data>/snapshots/` while TinyObs keeps running.
  Stopping TinyObs and copying the data directory also works.
- **Running in production.** TinyObs is one process on one machine. For a
  small production deployment:
  - set `--auth-token`;
  - listen on a non-loopback address;
  - terminate TLS with `--tls-cert`/`--tls-key`, or put TinyObs behind a
    reverse proxy;
  - schedule snapshots;
  - watch TinyObs's own `/metrics` (ingest, rejections, series versus cap,
    disk).

  It has no replication or high availability. When the node is down,
  monitoring is down, and the README says so.
- **V1 data** is not migrated. V2 uses a new default location, so V1 data stays
  untouched. V1 data was days old by design.

## 11. Testing

| Layer | What |
|---|---|
| Unit | labels, matchers, parser (valid and invalid input, error positions), OTLP and exposition-format translation |
| Conformance | the Prometheus PromQL test suite, as above |
| Storage | persistence across restart, retention, out-of-order and duplicates, series cap, concurrent append/select under `-race` |
| Crash recovery | a subprocess ingests while a test `kill -9`s it; after restart, every acknowledged sample is present |
| API | golden responses for every endpoint, including errors, checked against Prometheus's documented shapes |
| End to end | start the binary, scrape a test target and receive OTLP, query through the API; a Playwright smoke test of each UI page |
| Benchmarks | storage (ingest, bytes/sample, query), engine (range query at target scale); results in the README with the command that produced them |

CI runs `go vet`, `staticcheck`, `go test -race ./...` and the conformance suite.

## 12. What gets deleted

- `pkg/storage` (interface, memory and badger backends) and `pkg/compaction`.
- `pkg/query`: replaced by `pkg/promql` and `pkg/api`.
- `pkg/ingest`: handler, cardinality tracker, dashboard endpoints, WebSocket
  hub.
- `pkg/export`.
- `pkg/sdk/batch` and `pkg/sdk/transport`: replaced by an OTLP exporter.
- `pkg/config`: constants move next to their only users.
- `cmd/server`: becomes `cmd/tinyobs`.
- `web/index.html`: a redirect page.
- `QUICK_START.md` and `ARCHITECTURE.md`: folded into the README and this
  document.

## 13. What we will not build

- traces or logs;
- alerting, recording rules or notification channels;
- user accounts, roles, multi-tenancy, clustering, HA or replication;
- downsampling or long-term storage;
- a dashboard builder or dashboard import/export;
- native histograms, subqueries, or `@`;
- SDKs in other languages (OTLP and Prometheus client libraries cover them);
- a config file (flags only);
- Prometheus `remote_write` (for now).

## Roadmap

Each step is one PR against `main`, merged before the next begins, and each
leaves `main` working.

1. **This document** and ADRs 0001–0002.
2. **Engine:** storage (section 5), the query engine with conformance tests
   (section 7) and the Prometheus API (section 8).
   - Wired into the server; old storage, compaction, query and export are
     deleted.
   - The V1 JSON ingest endpoint stays for one PR, writing into the new
     storage, so the SDK and example keep working.
3. **Ingestion:**
   - scrape and OTLP (section 6);
   - SDK reworked to export OTLP;
   - `/v1/ingest` removed;
   - crash-recovery and end-to-end tests.
4. **Product:**
   - `cmd/tinyobs` as a single binary with the embedded UI (section 9);
   - self-metrics;
   - safe defaults (section 10).
5. **Release:**
   - README rewritten around the contract in section 1, with a compatibility
     table, benchmarks, and screenshots without browser chrome;
   - Dockerfile and Makefile updated;
   - tag `v2.0.0`.
